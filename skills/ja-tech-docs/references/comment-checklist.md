# コメントチェックリスト

## 先に確認すること

- 対象言語のドキュメンテーションコメント形式を確認する。
- Javadoc, KDoc, Rustdoc, Go Doc, TSDoc など、プロジェクトで採用している生成ツールや検査ツールの規約に従う。
- コメントの言語と用語は、ユーザーの依頼およびプロジェクトの方針に従う。
- 既存コメントのタグ, 句読点, 文体を正当な理由なく混在させない。

## コメントを書く対象

次のいずれかをコードだけでは明確に表現できない場合に書く。

- なぜこの実装が必要か
- 守るべき不変条件
- 非自明な前提条件
- 単位, 時刻, タイムゾーン
- 所有権, ライフタイム, 解放責任
- 並行処理, 排他, スレッド安全性
- 外部仕様との互換性のために、一見誤りに見える形にしている箇所
  (フィールド順や固定文言のすべてに互換性の注記を付けるのではなく、読者が「直したくなる」箇所に限る)
- 副作用
- 例外条件
- 性能上の制約
- 一見不要に見える処理を残す理由
- 回避策と、その回避策を削除できる条件

## 書かないコメント

- コードを日本語に読み替えただけの説明
- メソッド名や変数名の繰り返し
- 実装から確認できない設計理由
- 将来の予定を断定するコメント
- 「ここで処理する」など情報量のない説明
- コード変更によってすでに成立しなくなった説明
- 作業過程の判断を示すラベル (「互換性のため」「旧実装との差分」「〜と同じ判断」など):
  挙動そのものを現在の仕様の文として書き、判断の経緯は設計判断記録へ置く。
- 他モジュールや他システムとの比較, 横参照による正当化 (「foo モジュールの実装と同一」「bar サービスと同じ構成」):
  比較先が変わると成立しなくなる。
- リポジトリの開発規約の復唱 (この層で外部依存を直接使ってよい理由, 抽象化の層を設ける理由, 境界での値の変換規則など):
  規約は規約文書で一度だけ表現する。
- 呼び出し側がこの値をどう扱うか (インターフェースのコメントに「呼び出し元ではエラー応答になる」など):
  その契約は呼び出し側に書く。
- 環境構築や運用の手順 (起動コマンド, ポート番号, イメージの選定理由):
  README または運用手順へ置く。
- ファイルの種別を言うだけのヘッダー (「〜のテスト。」「〜の実装。」)
- 保留中の作業, 将来の予定, 現在の作業状態
- 応答一覧の再掲 (ステータスコードごとの本文やフラグの表など、コードとテストがすでに示している網羅的な列挙)

コメントを残す判断基準は、「その場のコードと一般的な知識だけを持つ読者が、これなしで誤解または見落としをするか」である。
残すコメントは、現在のコードの挙動と制約の記述として単独で意味が通る文にする。
旧実装や作業経緯との対比では書かない。

## 体裁

- 折り返しは [style-ja.md](style-ja.md) の「改行の規則」に従う。
  句点で改行し、読点では改行せず、固定幅で機械的に折り返さない。
- 丸括弧と空白は [style-ja.md](style-ja.md) の「表記の既定」に従う。
  半角括弧を使い、日本語との間に半角スペースを入れる。
- エンドポイントや対象名を示す見出し行
  (`// POST /foo`, `// GET {endpoint}/bars/{id}`) は句点なしで 1 行目に置き、説明は 2 行目から始める。
- 旧実装などの出所を記録する場合はファイル冒頭の 1 行に留め、
  複数の出所は半角カンマで区切る (`// 由来: legacy/foo.py, legacy/bar.py`)。
  出所ごとの補足説明は付けない。

## 公開 API コメント

内部アルゴリズムではなく、利用者が守る契約を説明する。
必要に応じて次を含める。

- API の目的
- 引数の意味, 有効範囲, null 許容性
- 戻り値と特殊値
- 例外またはエラー
- 副作用
- 非同期処理とキャンセル動作
- スレッド安全性
- 所有権
- 非推奨となった API と移行先
- 非自明な使用例

## 検査

- コメントが現在のシグネチャと実装に一致する。
- 引数名, 戻り値, 例外, 既定動作がコードと一致する。
- 生成ツールのタグやリンクが有効である。
- 利用可能なドキュメンテーションコメント用の lint または文書生成を実行する。
- コメントを追加したことで、コードより保守しにくい重複を作っていない。
