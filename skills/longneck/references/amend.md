# Longneckタスク定義改訂契約

## 目次

- 目的と成功条件
- 対象と変更内容の確定
- `description.md` の改訂
- `state.md` の整合
- 検証と報告

## 目的と成功条件

ユーザーが明示した変更だけを `description.md` へ反映し、改訂の帰結として必要な
`state.md` の整合をユーザー承認のもとで適用し、残タスクへの影響を報告する。
この契約は、ユーザーの明示指示を受けた `longneck-amend`、またはユーザーの変更指示を
受けて進行中の `longneck` 親が実行する。暗黙に実行しない。

成功条件は次のすべてとする。

- ユーザーが明示した変更だけが `description.md` へ反映されている。
- `state.md` への変更が、承認された整合案だけである。
- `task-format.md` のtemplate、構造、サイズ上限が守られている。
- 実際に文書を変更した場合だけ、`progress.md` の作業ログへ、改訂と適用した
  整合の要旨を含む `管理作業` の記録が1件追加されている。
- 対象内の変更が `description.md`、承認された整合による `state.md`、
  `progress.md` の管理作業ログだけである。
- 指示された変更が既に反映済みの場合は、更新日時と管理作業ログを含む
  一切の変更がない。
- 残タスクへの影響と、承認されず残る不整合が報告されている。

## 対象と変更内容の確定

1. `targeting.md` の共通手順でLongneckルートを確定する。完全一致のtitleの明示指定を
   必須とし、自動選択しない。`longneck` 親が実行する場合は、`targeting.md` の
   引き継ぎ規則に従い、進行中の確定済み root と title を再解決しない。
2. 実行主体が `longneck-amend` の場合は、CLIの `lock` で対象titleのロックを取得し、
   終了時に自分のtokenで解放する。`longneck` 親が実行する場合は、親が保持する
   ロックの下で行い、新たに取得しない。
3. ユーザーの変更指示を、`description.md` のどのセクション（目的、スコープ、
   非スコープ、完了条件、長期制約、主な作業対象）のどの意味を変えるかへ落とし込む。
   変更内容を一意に特定できなければ、不足する一点を具体的に聞き返す。ユーザー指示に
   ない変更を混ぜない。
4. CLIの `validate` を成功させ、`manifest` の結果を基準としてリポジトリ外の
   一時ファイルへ保存する。基準を `.longneck` や作業ツリーへ置かない。
   `validate` のエラーがある対象は、対象タスクの文書が壊れているため改訂しない。
5. `description.md` と `state.md` の全文、`issues.md` の未解決一覧を読み、変更が
   残タスクへ与える影響を把握する。

## `description.md` の改訂

1. 指示された変更が既に `description.md` へ意味として反映済みかを先に確認する。
   反映済みで正味の変更がなければ、`description.md`、`progress.md`、更新日時を
   含めて何も変更せず、`no_change` として報告する。
2. 適用直前に、開始時の基準を渡した `manifest-diff`（`--allow` なし）で変更が
   0件であることを確認する。変更があれば適用せず、「対象と変更内容の確定」から
   やり直す。
3. `task-format.md` のtemplateと構造を維持し、ユーザーが明示した変更だけを適用する。
   サイズ上限（100行・8 KiB）を超えないよう、意味を失わずに簡潔へ保つ。
4. 現在の進捗、残タスク、作業履歴、詳細調査を `description.md` へ書き込まない。
5. 実際に `description.md` を変更した同じ作業単位で、`progress.md` の `作業ログ`
   先頭へ `管理作業` の記録を1件追加し、改訂の要旨と、根拠がユーザー指示である
   ことを残す。
6. `issues.md`、`docs/`、他titleを変更しない。`state.md` の変更は、次の
   「`state.md` の整合」だけがユーザー承認のもとで行う。

## `state.md` の整合

`description.md` を実際に変更した場合だけ、その改訂の直接的な帰結として必要な
`state.md` の変更を整合案にまとめ、ユーザーの承認を得て適用する。`no_change` では
この節を実行しない。

1. 整合案に含めてよいのは次だけとする。改訂の帰結ではない再計画、タスクの整理、
   知見の追記を混ぜない。
   - 改訂後のスコープ・完了条件のもとで不要になった残タスクの削除
   - 新しい完了条件またはスコープに対して不足する残タスクの、`調査待ち` または
     `実行待ち` への追加。IDはCLIの `next-task-id` で採番する
   - 改訂により前提が変わった残タスクの、目的・完了条件・依存関係・区分の修正
   - 上記に伴う `現在のスナップショット`、`状態`、`更新日時` の同期
2. 整合案を、タスクごとの変更前後の要旨としてまとめて提示し、ユーザーの承認を
   得る。承認前に `state.md` を変更しない。一部だけが承認された場合は、承認された
   整合案だけを適用する。必要な整合がなければ提示を省略し、その旨を報告する。
3. 適用直前に、開始時の基準へ `--allow description.md --allow progress.md` を
   渡した `manifest-diff` で、承認を待つ間に対象内へそれ以外の変更が生じていない
   ことを確認する。`state.md` を含む許可外の変更があれば整合案を適用せず、
   `failed` として報告する。
4. 適用時は `task-format.md` の `state.md` の契約に従う。`description.md` の改訂で
   追加する同じ `管理作業` 記録へ、適用した整合の要旨、削除・修正したタスクID、
   根拠がユーザー承認であることを含め、削除済みIDの再利用を防ぐ根拠を残す。
5. 承認されなかった整合案と、整合案として提示できない広い再計画の必要性は、
   修正せず影響一覧として報告し、解消は `longneck` の進行またはユーザー判断へ
   委ねる。

## 検証と報告

CLIの `validate` を実行し、開始時に保存した `manifest` の結果を基準に、
`manifest-diff --baseline <保存したJSON> --allow description.md --allow progress.md`
（「`state.md` の整合」を適用した場合は `--allow state.md` を加える）で、対象内の
変更が許可した文書だけである（`no_change` では変更が0件である）ことを確認する。

次のいずれかの `status` で報告する。

- `amended`: 明示された変更と、承認された整合を適用し、検証が成功した。
- `no_change`: 指示された変更が既に `description.md` へ反映済みで、正味の変更がない。
- `needs_user`: 変更内容を一意に特定できず、聞き返しが必要である。
- `failed`: 検証失敗、書込み失敗、または基準fingerprintとの不一致を検出した。

statusに加えて、改訂前後の差分の要旨（`no_change` では反映済みと判断した根拠）、
適用した整合と承認されず見送った整合、影響を受ける残タスクID、推奨する後続
（例: `longneck` での再計画）を返す。
コミットの要否はユーザー指示とプロジェクト固有ルールに従う。
