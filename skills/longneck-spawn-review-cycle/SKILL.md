# レビューサイクルのLongneckタスクを作る

レビュー対象を確定し、レビュー, 修正案, 修正を繰り返すタスク一式を作成する。
作成の手順は `longneck-spawn` に従い、入力の確定と文書内容の組み立てをこのスキルの規則で置き換え、結果の報告へ項目を加える。
呼出しの形は `longneck-spawn-review-cycle <タスク名> <タスク内容>` とする。
`<タスク名>` は、作成するLongneckタスクのtitleを指す。
`<タスク名>` の指定がない場合は、「titleを決める」に従って命名する。

## 必須契約を読む

最初に次を全文読む。

- [longneck-spawn の SKILL.md](../longneck-spawn/SKILL.md): 作成の手順
- [task-format.md](../longneck/references/task-format.md)
- [operations.md](../longneck/references/operations.md)
- [targeting.md](../longneck/references/targeting.md)
- [cycle-protocol.md](references/cycle-protocol.md): 作成したタスクを進める子と親が従う規約
- [task-template.md](references/task-template.md): 4文書のテンプレート

どれかが見つからない場合は、推測で作成せず、Longneckスキル群の不足を報告する。

## 入力を確定する

最初に、`longneck-spawn` の「入力を確定する」のうち、次の3つの手順を実行する。

- ユーザーの最新指示と、適用される `AGENTS.md` の確認
- Longneckルートの確定
- 既存titleと壊れたentryの確認

その後、同じ節のほかの手順（目的, スコープ, 完了条件の特定など）の代わりに、次を確定する。
確定できない項目は、不足する一点を具体的に聞き返す。

### レビュー対象

タスク内容から、レビュー対象と、対象を再現可能に列挙する方法を確定する。
修正は、対象のファイルの現在の内容（Gitリポジトリ内では作業ツリーにある内容）へ実施する。
そのため、対象の最新の状態がそこにあることを確認する。
対象の種類によらず、`.longneck` 配下は対象に含めない。
差分, 未追跡ファイルの列挙, ディレクトリの展開に `.longneck` 配下のパスが現れる場合は、そのパスを除く。
対象が空の場合は作成せず、その旨を報告する。
対象が空であるとは、下の各項目の方法で列挙した対象が1つもないことを指す。
差分にも未追跡ファイルにも対象がない場合, コミット群が変更した箇所が作業ツリーに1つも現存しない場合,
指定されたファイルが1つも存在しない場合が、これに当たる。
指定されたファイルの一部だけが存在しない場合は、存在しないパスを示して、対象の指定を聞き返す。

- 未コミットの変更:
  作成時の `HEAD` のコミットIDを基準コミットとして記録する。
  コミットが1件もなく、`HEAD` がコミットを指さないリポジトリでは、基準コミットを定められない。
  この場合は、その旨を伝え、特定のファイル群での指定を求める。
  対象は、基準コミットから作業ツリーまでの差分（`git diff <基準コミット>`）と、
  ignoreされていない未追跡ファイル（`git ls-files --others --exclude-standard`）とする。
  未追跡ファイルの列挙は、追跡されていない別のGitリポジトリを、ディレクトリのパスとして出力する。
  作業ツリーでディレクトリであるパスは、対象に含めない。
  基準コミットで定めるのは、修正をコミットした後も同じ対象を列挙できるようにするためである。
- 特定のコミット群:
  指定されたコミット群が `HEAD` の履歴に含まれること（各コミットが `HEAD` の祖先、
  または `HEAD` 自身であること）を確認する。
  確認には `git merge-base --is-ancestor <コミットID> HEAD` を使える。
  含まれない場合は、ブランチを切り替えずにユーザーへ確認する。
  連続した1本の範囲で、末尾が `HEAD` であり、
  範囲の途中のマージコミットが、指定されていないコミットを取り込んでおらず、
  範囲の先頭のコミットの親が1つだけの場合は、
  その親を基準コミットとし、対象を基準コミットから作業ツリーまでの差分とする。
  それ以外の場合（末尾が `HEAD` でない、連続しない複数のコミットである、
  範囲の先頭がルートコミットまたはマージコミットである、
  範囲の途中のマージコミットが、指定されていないコミットを取り込んでいる）は、対象をコミットIDの一覧で定める。
  この場合の対象は、そのコミット群が変更した箇所のうち、作業ツリーに現存するものとする。
  `対象の特定方法` には、コミットIDの一覧と、変更箇所を `git show <コミットID>` で特定することを書く。
  一覧にマージコミットがある場合は、そのコミットの変更箇所を、
  第1の親との差分（`git diff <コミットID>^1 <コミットID>`）で特定することも書く。
  マージコミットに対する `git show` は、競合のないマージでは差分を出力しないためである。
- GitHubのPR:
  `gh` コマンドを使える環境でだけ扱う。
  `gh pr view <番号> --json baseRefOid,headRefOid` でPRの情報を取得する。
  ローカルの `HEAD` がPRの先頭のコミット（`headRefOid`）と一致することを確認する。
  一致しない場合は、ブランチを切り替えずにユーザーへ確認する。
  PRに記録されているベースブランチのコミット（`baseRefOid`）がローカルにあることを、
  `git cat-file -e <baseRefOid>^{commit}` で確認する。
  ある場合は、`git merge-base <baseRefOid> HEAD` の結果を基準コミットとする。
  ローカルのベースブランチは古い場合があるため、基準コミットの計算に使わない。
  `git merge-base` が共通の祖先を出力しない場合は、基準コミットを推測せずに、ユーザーへ確認する。
  履歴が途中までしかないリポジトリと、履歴を共有しないブランチでは、共通の祖先が見つからない場合がある。
  `baseRefOid` のコミットがローカルにない場合は、取得（fetch）を自分で実行せずに、ユーザーへ確認する。
  対象は、基準コミットから作業ツリーまでの差分とする。
  `gh` コマンドを使えない場合は、その旨を伝え、特定のコミット群での指定を求める。
- 特定のファイル群（Gitリポジトリの内外を問わない）:
  ユーザーがファイルをパスで指定し、差分やコミットを指定していない場合に使う。
  対象のファイルのパスを一覧として記録する。
  ディレクトリが指定された場合は、作成時に配下のファイルを列挙し、ファイルのパスの一覧へ展開して記録する。
  Gitリポジトリ内では、追跡されているファイルと、ignoreされていない未追跡ファイルを列挙する
  （`git ls-files --cached --others --exclude-standard -- <ディレクトリ>`）。
  このコマンドは、作業ツリーで削除され、削除がステージされていないファイルも出力する。
  作業ツリーに存在しないファイルは、一覧へ含めない。
  このコマンドは、マージの競合が未解決であるファイルのパスを、複数回出力する。
  同じパスは、一覧へ1回だけ記録する。
  このコマンドは、サブモジュールと、追跡されていない別のGitリポジトリを、ディレクトリのパスとして出力する。
  作業ツリーでディレクトリであるパスは、一覧へ含めない。
  作成後にそのディレクトリへ追加されたファイルは、サイクルの修正で作成されたものを除き、対象に含めない。
  Longneckルートの配下にあるファイルはLongneckルートからの相対パスで書き、それ以外のファイルは絶対パスで書く。
  対象は一覧にあるファイルの全体とし、差分へ読み替えない。
  基準コミットは記録しない。

作成時の作業ツリーに、上の各項目の方法で対象として列挙される範囲にあり、
レビュー対象に含めない変更がある場合は、そのパスを非スコープへ記録する。
列挙される範囲にない変更は、記録しなくても対象にならないため、記録しない。
含めない変更が、対象と同じファイルにある場合は、パスに加えて、含めない変更の場所（見出し, 関数名など）を記録する。
含めるかどうかを判断できない場合は聞き返す。

対象を基準コミットから作業ツリーまでの差分で定めた場合、作成後に作業ツリーへ加えられた変更は、
サイクルの修正によるものでなくても対象に含まれる。
各サイクルで、作業ツリーの現在の内容から対象を列挙し直すためである。

### 任意の指定

タスク内容に指定がある場合だけ反映し、なければ既定値を使う。
指定がないことを理由に聞き返さない。

- レビュー観点: 既定は指定なし（`cycle-protocol.md` の既定の観点に従う）。
- レビューと修正案を担当する子のモデル, 修正を担当する子のモデル:
  既定はどちらも指定なし（親と同じモデルを継承する）。
  ユーザーは2つを別々に指定できる。
  モデル名は、ユーザーが指定した名前をそのまま記録する。
- 継続確認の間隔: 既定は5サイクル。
  1以上の整数だけを受け付ける。
  それ以外の値が指定された場合は、値を聞き返す。

### コミット方針

修正による変更をコミットするかどうかを、タスクを作成する前に、次の2つのどちらかへ確定する。

- `コミットしない`: 修正による変更を作業ツリーに残す。
- `修正のタスクごとにコミットする`: 修正のタスクの担当が、そのタスクで加えた変更をコミットする。

次の順で決める。

1. タスク内容にユーザーの指示があれば、それに従う。
2. 指示がなければ、適用される `AGENTS.md` などのプロジェクト固有のルールが、
   エージェントによるコミットを求めているか、禁じているかを確認し、それに従う。
3. どちらからも決められない場合は、推測せずに、ユーザーへ2つのどちらにするかを確認する。
   「任意の指定」の「指定がないことを理由に聞き返さない。」は、この確認には適用しない。

確認するときは、次の2つを伝える。

- 対象を基準コミットから作業ツリーまでの差分で定めた場合に `コミットしない` を選ぶと、
  修正による変更と、ユーザーが作業ツリーへ加える変更を、Gitの差分では区別できなくなること
- `修正のタスクごとにコミットする` を選んでも、修正の前から未コミットの変更があるファイル
  （未追跡のファイルを含む）への修正は、コミットされずに作業ツリーへ残ること

対象がGitリポジトリ外にある場合はコミットできないため、確認せずに `コミットしない` とする。

作成時の作業ツリーに、「レビュー対象」の各項目の方法で対象として列挙される範囲にある未コミットの変更
（未追跡のファイルを含む）がある場合は、`修正のタスクごとにコミットする` を選べない。
レビュー対象に含めない変更として非スコープへ記録する変更も、この未コミットの変更に含める。
修正が、コミットされずに作業ツリーへ残るためである。
ユーザーの指示またはプロジェクト固有のルールがこの方針を求めている場合も、同じとする。
ユーザーの指示またはプロジェクト固有のルールにより `コミットしない` に決まる場合は、確認せずに `コミットしない` とする。
それ以外の場合は、2つの方針のどちらにするかを確認する代わりに、選べない理由を伝え、次のどちらにするかをユーザーへ確認する。
指示またはルールが `修正のタスクごとにコミットする` を求めている場合と、指示とルールのどちらからも決められない場合が、これに当たる。

- `コミットしない` で作成する。
- 作成を中止する。ユーザーが変更をコミットした後の依頼で、対象を確定し直して作成する。

### `永続化対象外` の宣言

タスクを作成する前に、テンプレートの `永続化対象外` の宣言の内容（列挙する3つの範囲）と帰結をユーザーへ示す。
そのうえで、宣言を含めることへの同意を確認する。
示す帰結は次の3つである。

- `longneck-sever` でタスクを削除するとき、
  レビュー結果, 修正案, 台帳, サイクルの経緯, タスク定義は `.longneck` 外へ永続化されずに失われる。
- `longneck-flush` で `state.md` と `progress.md` をスリム化するときも、
  この2文書にあるサイクルの経緯は `.longneck` 外へ永続化されずに除去される。
- 宣言の範囲に該当しない知見（`issues.md` へ記録された範囲外の問題など）と、
  該当するかを確定できない知見は、通常どおり永続化の対象になる。
  重大なセキュリティ, プライバシー, データ損失の懸念は、宣言の範囲に含まれる場合も永続化の対象になる。

この確認は、起動が明示か暗黙かにかかわらず、作成のたびに行う。
「任意の指定」の「指定がないことを理由に聞き返さない。」は、この確認には適用しない。
回答に応じて次のように扱う。

- ユーザーが同意した場合だけ、`description.md` へ `永続化対象外` のセクションを含める。
- ユーザーが同意しなかった場合は、セクションを省いて作成する。
  作成は中止しない。
- 回答が同意かどうかを確定できない場合は、同意として扱わず、聞き返す。

同意の確認は、タスクを作成する前に終える。
作成後の結果報告を同意の確認の代わりにしない。

## titleを決める

`longneck-spawn` の「titleを決める」に従う。

## 文書内容を組み立てる

[task-template.md](references/task-template.md) のテンプレートへ、確定した値を入れて4文書を用意する。
テンプレートの構成を変更しない。
`永続化対象外` のセクションは、ユーザーが同意した場合はテンプレートの内容のまま含め、
同意しなかった場合はセクションごと省く。
含める場合は、列挙する範囲の一部を省かず、範囲の内容も書き換えない。
日時はCLIの `now` が出力する現在時刻を使う。

- 最初のタスクは `T-0001 — サイクル001: レビュー` とし、`実行待ち` へ置く。
- レビューと修正案のモデルが指定された場合だけ、`T-0001` に `- モデル:` 行を置く。
- 修正案と修正のタスクは作成時に用意しない。各段階の子が、結果に応じて追加する。

## 原子的に作成する

`longneck-spawn` の「原子的に作成する」に従う。
作成後に `longneck` を自動起動しない。

## 結果を返す

`longneck-spawn` の「結果を返す」の項目に加えて、次を返す。

- 確定したレビュー対象と、対象の特定方法
- 対象を基準コミットから作業ツリーまでの差分で定めた場合:
  作成後に作業ツリーへ加えた変更は、サイクルの修正によるものでなくても、レビューと修正の対象に含まれること
- レビュー観点, モデルの指定, 継続確認の間隔
- 確定したコミット方針と、確定の根拠（ユーザーの指示, プロジェクト固有のルール, 確認への回答, 対象がGitリポジトリ外にあることのいずれか）
- コミット方針が `修正のタスクごとにコミットする` の場合:
  修正の前から未コミットの変更があるファイル（未追跡のファイルを含む）への修正は、コミットされずに作業ツリーへ残ること
- `description.md` へ `永続化対象外` の宣言を含めた場合:
  宣言により、「`永続化対象外` の宣言」の節にある3つの帰結が生じること（3つの帰結の内容を省かずに伝える）
- 宣言を省いた場合:
  `description.md` に `永続化対象外` の宣言がないこと。
  そのため、`longneck-sever` でタスクを削除するとき、
  レビュー結果, 修正案, 台帳, サイクルの経緯を含むすべての知見が永続化の調査対象になること
- タスクを進めるには `longneck` を使うこと

ユーザーが同じ依頼で実行開始も明示した場合の扱いは、`longneck-spawn` の「結果を返す」に従う。
